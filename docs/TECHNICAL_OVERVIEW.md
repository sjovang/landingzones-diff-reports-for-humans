# Technical overview

ALZ Release Brief compares published releases of the Azure Landing Zones
Library and produces deterministic reports for the `platform/alz/` library
configuration. It does not inspect Azure environments or certify that an
upgrade is safe.

## Architecture

- **Web app:** SvelteKit and TypeScript with the Node adapter, suitable for Azure App Service.
- **Release discovery:** An hourly Azure Functions timer discovers ALZ tags through GitHub's API and stores resolved commit SHAs in a durable catalog. Web requests and report jobs read that catalog rather than calling GitHub. The upstream repository is fixed in server code.
- **Comparison processing:** An Azure Functions Node.js v4 queue trigger consumes `report-jobs` messages and analyzes complete stored `platform/alz/` inventories. This avoids relying on GitHub Compare's 300-file ceiling.
- **Durable state:** Azure Queue Storage holds work, Table Storage holds job and cache metadata, and private Blob containers hold report JSON, the release catalog, and content snapshots.
- **Local services:** Azurite emulates Queue, Blob, and Table Storage.

The hosted app and worker use managed identity through `DefaultAzureCredential`
and identity-based Functions storage settings. Grant only the required
data-plane roles. Local development uses Azurite and does not need cloud
credentials. A server-side `GITHUB_TOKEN` is optional for a higher GitHub API
rate limit and is used only during release discovery; it must never be exposed
to the browser.

## Release catalog and comparison data

The timer's `RELEASE_SYNC_SCHEDULE` setting is a six-field NCRONTAB expression
in UTC, defaulting to `0 0 * * * *` (hourly). Each sync lists matching ALZ tags
with one request. Lightweight tag commits come directly from that listing;
unchanged annotated tags reuse their stored resolution. Catalog updates are
atomic and guarded by the previous Blob ETag, so concurrent syncs cannot
overwrite a newer catalog. GitHub errors, incomplete discovery, or snapshot
warm-up failures retain the last successful catalog.

`/api/releases` includes `syncedAt`; its contents represent that sync, not a
live assertion that tags are still published. An empty store returns an
actionable 503 rather than falling back to GitHub on each request.

ALZ contents are stored in `releases/snapshots-v1/<commit-sha>.json` and reused
across comparison pairs and process restarts. The newest two releases are
warmed during sync; older releases are fetched by immutable commit via Git and
stored when first compared. Concurrent requests in one process share that
fetch; independent worker instances may fetch the same missing snapshot
concurrently, but conditional Blob creation prevents replacement. Comparison
generation makes no GitHub REST calls. Moved or removed tags are reflected
after the next successful sync; a queued comparison fails explicitly if its
selected tags no longer match the catalog. Existing completed reports remain
available by job ID.

Completed reports are reused by repository, ALZ path, commit SHAs, and report
schema version. Report schema version 5 is part of the cache key, so older
reports (including those missing deprecation-only classification) are not
reused. Polling an old job returns an explicit instruction to start a new
comparison rather than serving an incompatible report.

## Change evaluation and display rules

This is the current implemented behavior of ALZ Release Brief, not a proposed
ideal model. Use the rule IDs below when discussing changes to classification,
wording, visibility, and ordering. Report schema: **5**.

Analysis is deterministic; report explanations are not generated by AI.

## 1. Evaluation versus presentation

| Layer | Responsibility | Main implementation |
| --- | --- | --- |
| Source selection | Resolve two release tags to immutable commits and retrieve complete ALZ inventories | [release-catalog.ts](../src/lib/server/release-catalog.ts), [git-report.ts](../src/lib/server/git-report.ts) |
| Evaluation | Identify entities and changes; resolve assignment context; produce facts, warnings, and a summary | [analysis.ts](../src/lib/server/analysis.ts) |
| Report contract | Carry status, deprecation flags, versions, facts, warnings, and assignment context | [types.ts](../src/lib/types.ts) |
| Assignment presentation | Compare paired assignment fields for concise before/after display | [assignment-changes.ts](../src/lib/assignment-changes.ts) |
| Report presentation | Choose icons, labels, visible detail sections, search fields, and disclosure behavior | [+page.svelte](../src/routes/+page.svelte) |

Changing an icon or collapsing evidence is a presentation change. Changing which
entities qualify, how effects resolve, or how deprecation-only status is assigned
is an evaluation change and affects cached report contents.

## 2. Scope, identity, and inclusion

| ID | Current rule | Consequence |
| --- | --- | --- |
| E01 | Compare only `platform/alz/` in the fixed upstream `Azure/Azure-Landing-Zones-Library`. Any two distinct catalog releases may be selected; chronological ordering is not required. | SLZ and AMBA are excluded. “Before” and “after” follow the chosen direction, even for a reverse comparison. |
| E02 | Analyze both complete inventories, not only changed files or the GitHub comparison view. | Unchanged policies can appear because their assignments changed. GitHub comparison display limits do not limit evaluation. |
| E03 | Parse every `.json` file as an object. Identity is `kind:name`; missing `name` falls back to the file path. Kind comes from the containing directory. | A named entity can retain identity when relocated. A renamed entity is generally a removal and addition, not a detected rename. |
| E04 | Invalid JSON, non-object JSON, or duplicate identity within one inventory fails the comparison explicitly. | No partial, success-shaped report is produced for these failures. |
| E05 | JSON object-key order and whitespace do not affect equality. Array order does affect equality. | Formatting-only JSON changes do not produce entries. Array reordering can produce an entry even without a behavioral change. |
| E06 | Include an entity if it exists on only one side, its parsed value changes, its path changes, or its resolved assignment context changes. | A report entry is not synonymous with a changed definition file. |
| E07 | Exclude non-JSON files whose basename matches `README` or `README.<extension>`, case-insensitively. Other changed non-JSON files remain as supporting content. | README changes do not contribute to report-entry totals; they can still contribute to the raw changed-file count. A JSON file is evaluated as JSON before this non-JSON exclusion. |
| E08 | `.md` supporting files are documentation; other unrecognized paths are configuration. Roles and generic configuration have no specialized behavioral analysis. | Keep source evidence and explicitly state that interpretation is unavailable. |

The raw changed-file count compares stored file strings, whereas entity inclusion
uses parsed semantic equality. These counts need not match.

## 3. Status and deprecation

| ID | Current rule | Display/result |
| --- | --- | --- |
| C01 | Absent before, present after: `added`. Present before, absent after: `removed`. Present on both sides and included by E06: `modified`. | Green plus, red minus, or blue update icon respectively. |
| C02 | A current policy or initiative is deprecated only when `properties.metadata.deprecated === true`. | Orange warning icon. A name prefix, version suffix, or removal alone is not evidence of deprecation. |
| C03 | Deprecation is a flag, not a fourth primary status. It can already be true before the comparison. Removed items do not get the current-release deprecation flag. | Substantive modifications to a deprecated definition retain update and deprecation icons. Added deprecated definitions retain added and deprecation icons. |
| C04 | A definition qualifies as `deprecationOnly` only under the exact normalization rules below. | Show the orange icon alone; suppress the blue update icon. Primary status remains `modified`. |
| C05 | Count entries by primary status, including context-only and deprecation-only entries. | Deprecation-only still contributes to “updated”; there is no separate deprecated total. |

### C04: exact deprecation-only decision

All of these must hold:

1. The same policy or initiative exists on both sides at the same path.
2. The previous version exists and the current version equals that exact version
   plus `-deprecated`.
3. Previous metadata does not have `deprecated: true`; current metadata does.
4. The full definition objects are equal after only these normalizations:
   - Ignore metadata `version` and `deprecated`.
   - Ignore a newly introduced metadata `supersededBy` on the current side when
     it was absent before. A changed existing value is not ignored.
   - Remove a leading `[Deprecated]:` and following whitespace from the current
     display name.
   - Remove an exact appended description suffix
     ` Superseded by https://www.azadvertizer.net/<category>/<supersededBy>.html`,
     when current metadata supplies the replacement. Category is
     `azpolicyadvertizer` for policies or `azpolicyinitiativesadvertizer` for initiatives.
   - Normalize a current `properties.version` that equals the suffixed old
     version back to its previous value.

Rules, parameters, and all remaining content must match. A version change from
`2.0.0` to `2.1.0-deprecated`, arbitrary description changes, or relocation does
not qualify.

**Important boundary:** C04 compares the definition, not its assignments.
Assignment changes can coexist with `deprecationOnly` and remain visible in
details even though only the orange icon is shown.

## 4. Definition facts

| ID | Entity/field | Current explanation |
| --- | --- | --- |
| F01 | Version | Prefer metadata `version`, then `properties.version`. Different versions generate a before/after fact, not a claim that behavior changed. |
| F02 | Purpose and naming | Use current display name and description, or previous values for removals. Changes in description, display name, and metadata receive separate facts. |
| F03 | Policy parameters | Explain additions, removals, defaults, allowed values, types, and parameter metadata. Other parameter constraints are flagged for source review. |
| F04 | Policy rule | Always show the definition's default effect. Compare the `if` condition, `then` action, and evaluation mode separately. If the full rule matches, explicitly say it is unchanged. |
| F05 | Policy action details | Detect changes to deployment/existence/property-operation details but do not translate them into deployment outcomes. Additional action properties require review. |
| F06 | Initiative membership | Pair members by `policyDefinitionReferenceId`, falling back to referenced ID, then “Unnamed member.” Explain additions/removals, changed references, version selectors, parameter bindings, and policy groups. |
| F07 | Newly added initiative members | Explain the bundled policy's effect using initiative defaults and member bindings when its version selector matches. Say assignments can override it. Unavailable definitions or unmatched versions remain unresolved. |
| F08 | Assignment definitions | Explain changed target definitions, explicit parameter values, and definition-version selection. Changed overrides and resource selectors require source review. |
| F09 | Archetypes | Explain added/removed policy assignments, policy definitions, policy-set definitions, and role definitions by membership. |
| F10 | Architectures | Pair management groups by ID. Explain added/removed groups, changed archetypes, and changed parent IDs. Other group changes receive a generic “changed” fact. |
| F11 | Unsupported properties | For policies, initiatives, and assignments, changes outside the known properties generate a source-review warning. Other unhandled content may receive generic warnings rather than a precise field-level explanation. |

Supported condition translation includes `allOf`, `anyOf`, `not`, field tests,
limited counts, and these operators: `equals`, `notEquals`, `in`, `notIn`,
`contains`, `notContains`, `like`, `notLike`, `match`, `notMatch`, `greater`,
`greaterOrEquals`, `less`, `lessOrEquals`, and `exists`.

Condition translation has a shared **50-node budget** for previous/current
conditions. Unsupported structures or expressions add warnings, including when
a partial explanation can be produced. Expression-based existence tests are
not treated as false.

## 5. Assignment context and applicability

| ID | Current rule | Meaning |
| --- | --- | --- |
| A01 | Discover direct assignments and policies referenced through assigned initiatives using bundled identities. | Reference lookup uses the terminal ID name and distinguishes policy versus initiative. Missing built-ins are not fetched or guessed. |
| A02 | Direct policy values are policy defaults overridden by explicit assignment parameters. | Definition defaults and configured assignment effects are distinct information. |
| A03 | For initiative members, first resolve initiative defaults overridden by assignment parameters. Resolve member bindings against those values and overlay them on policy defaults. | Only exact `[parameters('name')]` or double-quoted equivalents are substituted. No general expression evaluation occurs. |
| A04 | A version selector matches when absent, exactly equal to the bundled version, or a three-component numeric/wildcard pattern matching a three-component numeric bundled version. | An unmatched selector makes the effect unresolved. A wildcard is a selection, not an exact resolved version. |
| A05 | Interpret supported effects by name, case-insensitively. | Audit reports; Deny blocks matching requests; Disabled disables evaluation; AuditIfNotExists audits related resources; DeployIfNotExists can deploy/update; Modify can change properties; Append adds properties; DenyAction blocks specified actions; Manual requires attestation. Unknown names require review. |
| A06 | Resolve scopes through assignment membership in archetypes and those archetypes' management-group mappings in each architecture. | Show direct library mappings, not all inherited descendants or a deployed environment. |
| A07 | An unmapped archetype is explicitly labeled. If no archetype-derived scopes exist, use a declared scope only when it does not match `placeholder`, `contoso`, or `${`. Otherwise say no scope resolved. Append excluded scopes separately. | Do not invent scope from deployment placeholders. |
| A08 | `DoNotEnforce` is separate from the configured effect. `Default` or missing mode means normal enforcement; other values require review. | A configured Deny with DoNotEnforce does not mean this assignment blocks requests. |
| A09 | Overrides make the effect require source review. Resource selectors receive applicability notes; their actual selection is not calculated. | Do not assert resolved override behavior or resource targeting. |
| A10 | No current assignment produces a warning that adding a definition does not assign/enforce it. Context-bearing entries also warn that scopes are library configuration, not deployed state. | Presence of a definition is not proof of enforcement. |
| A11 | Compare context including assignment identity/name, referenced definition ID, effect, enforcement, scopes, parameters, and notes. Exclude source URLs and formatted definition title/version fields. | Source commit changes alone do not make every policy look changed. Merely bumping an initiative's metadata version does not automatically include all its unchanged member policies. |

Context comparison currently preserves array order and sorts contexts by their
serialized contents. It is not a fully order-independent set comparison.

## 6. Summary precedence

**S01:** The evaluator selects one lead summary, in this order:

1. Added.
2. Removed.
3. Deprecation-only: marked deprecated; rules and parameters unchanged.
4. Definition version changed: old version to new version.
5. Definition value unchanged but assignment context changed: use S02.
6. Otherwise: generic definition updated.

**S02:** For context-only changes, prefer:

1. A paired assignment now references a different definition ID: name its new
   definition and bundled version.
2. Scope changes.
3. Configured effect changes.
4. Enforcement changes.
5. Otherwise: assignment parameters or version selections changed.

Append “The [kind] definition is unchanged.” Only the first applicable summary
reason is chosen. Other changes remain in facts and assignment details.

This precedence is a tuning point: a version bump currently outranks a changed
effect or rule in the lead summary. The summary is not a severity rating or
exhaustive list of differences.

## 7. Display rules

| ID | Current rule |
| --- | --- |
| D01 | Sort kinds: policy, initiative, assignment, archetype, architecture, role, configuration, documentation. Sort by title within each kind. No impact/severity ranking. |
| D02 | Collapsed rows show status icons, title, kind, summary, and version. A version transition is emphasized only when both versions exist and differ. |
| D03 | Expanded content begins with the same lead summary, then assignment deltas, purpose/description, definition facts, full assignment context, interpretation notes, and source evidence. |
| D04 | Pair assignment deltas by assignment ID. Show changed name, formatted referenced definition, effect, enforcement, scopes, parameters/version selections, and notes with labeled Before/After values. Sort scope/parameter/note arrays for this display comparison. Join array values with semicolons; empty arrays become “None.” Source URLs are ignored. |
| D05 | Added/removed assignment deltas show “Not assigned → Present” or “Present → Removed.” For paired assignments, list unchanged effect, enforcement, scopes, and parameters/version selections only when at least one compared field changes. |
| D06 | Full previous context shows changed assignments for non-added entries when the contexts differ. Full current context shows changed assignments when contexts differ, or all current assignments otherwise. Removed entries have no current section. Empty sections are omitted. |
| D07 | Preserve warnings and commit-pinned sources. Coverage warnings appear only for incomplete reports. Complete source coverage is not a guarantee that every expression is interpreted. |
| D08 | Search is a case-insensitive substring over title, description, summary, facts, and previous/current scopes. Warnings, all assignment fields, and source labels are not independently indexed. Filtering does not change totals or evaluation. |
| D09 | Native disclosure details render on demand. Search preserves expanded state; a new comparison resets it. |

## 8. Worked examples

| Scenario | Evaluation | What the reader sees |
| --- | --- | --- |
| Same policy, same rule; network assignment switches initiative `2.0.0` to `2.1.0` with a different initiative ID | Context-only `modified` policy | Blue icon; definition unchanged summary; exact referenced-definition Before/After; unchanged settings listed. |
| Policy version `1.1.0 → 1.2.0`, no rule changes | `modified`, not a behavioral-change classification | Blue icon; version transition and unchanged evaluation-rule fact. |
| Initiative `2.0.0 → 2.0.0-deprecated`, only permitted deprecation announcements differ | `modified`, `deprecated`, `deprecationOnly` | Orange icon alone; deprecation summary; still counted as updated. |
| Same suffix change plus a changed rule, parameter, or other non-normalized content | `modified`, `deprecated`, not `deprecationOnly` | Blue and orange icons; facts/source warnings expose additional changes. |
| Policy default Audit; assignment overrides it to Deny with DoNotEnforce | Default and configured effect resolved separately | Audit default, configured Deny, and explicit non-enforcement explanation. |
| New unassigned policy | `added`; no current assignment | Green icon and explicit warning that adding a definition does not enforce it. |
| Initiative refers to a built-in definition absent from inventory | Include applicable membership change; interpretation unavailable | Referenced identity/version selector and source-review warning, not guessed behavior. |
| Only source formatting or README content changes | No semantic entry for those changes | No added/updated/removed entry; raw changed-file count can still differ. |

## 9. Known tuning boundaries

These are current limitations or product decisions, not changes authorized by
this document:

- “Updated” combines definition, metadata, relocation, and assignment-context
  changes. There is no separate behavior-change or context-only status field.
- Deprecated means current state, not necessarily newly deprecated.
- Deprecation-only icons describe definition changes and can hide the separate
  fact that assignment applicability changed; the detailed explanation retains it.
- Version-first summaries can overshadow more consequential facts.
- Full previous/current context repeats unchanged information after the concise
  delta. It could become secondary evidence without discarding it.
- Evaluator context equality and display delta equality are different. Display
  uses formatted reference text and order-independent arrays; evaluator excludes
  formatted title/version fields and preserves arrays. A rendered delta need
  not be the reason an entry was included.
- Array reorderings and changes outside specialized interpretation can result
  in generic updates. Exact structured values and complex expressions remain
  source-review cases rather than complete prose diffs.
- The tool does not calculate severity, upgrade recommendations, compliance
  outcomes, deployment changes, or remediation success.

## 10. How to tune a rule

For each proposed change, record the **rule ID**, triggering source scenario,
current output, desired output, information that must remain available, and
counterexample where the rule must not apply.

For evaluation changes, update evaluator tests and consider incrementing
`REPORT_SCHEMA_VERSION`: the cache key includes that version, and old immutable
reports are not retroactively reinterpreted. For presentation-only changes,
update browser/helper tests; existing report data can generally be reused.

Regression references:

- [analysis.test.ts](../src/lib/server/analysis.test.ts): formatting, scope/context
  propagation, version-only changes, deprecation-only decisions, effects,
  selectors, missing definitions, unsupported conditions, and explicit failures.
- [assignment-changes.test.ts](../src/lib/assignment-changes.test.ts): exact deltas,
  unchanged settings, additions/removals, source and ordering exclusions.
- [page.e2e.ts](../src/routes/page.e2e.ts): icons, detail content, before/after
  presentation, responsive layout, search/disclosure, and report restoration.

Keep this document synchronized with those implementations. Proposed behavior
should be labeled as proposed until the code and corresponding fixtures agree.
